# 复盘

## 最难的问题

真实服务的格式修复比单个工具函数更难定位。草稿已经通过检查，最终回复却带着 Markdown；要求修正 JSON 时又遇到 HTTP 400。问题出在完整消息回合的衔接。Codex 修改回合边界后，另做诊断并重跑业务场景，才有依据记录为已修复。过程和失败证据见[接入记录](12-post-checkpoint-acceptance.md)。

验收器本身也出现过问题。1 秒请求可以合理停止，教学中的界面特写也能承担展示作用。如果预期过严，正确行为仍会被判失败。因此原始判定继续保留，更正理由和复核结果另行记录。

## 学习收获

完成状态要建立在实际工具回执上。模型结束和业务成功存在区别，给每版草稿计算标识，再核对同一标识的时长与规则记录，才能避免修改稿借用旧稿的通过结果。

测试需要证明观察后的动作变化。单纯缩短输入时长，模型可能首稿就合规，无法证明压缩修订能力。使用此前真实生成的 14.2 秒稿件，再把上限改为 10 秒，得到了原稿诊断、模型压缩和复检的完整证据。最终 8.3 秒说明这条路径执行过，不能推导所有素材都能同样压缩。

复用代码也需要说明职责和代价。本次保留熟悉的模型与工具接口，减少重新搭建的工作；严格引用原文便于核查事实，同时限制了表达。这些取舍比单独列出框架名称更能解释当前结果。

## 下一步

优先扩充合成资料与不同创作要求，重复运行并统计失败类型，再决定是否引入语义改写检查。下一轮验证应分别观察来源支持是否准确、约束能否满足，以及失败后是否采取合理动作。

实际配音校准需要单独完成，比较估计时间与录音时间。镜头和文案质量还需要独立人工评审，当前结构检查无法替代创意评价。
